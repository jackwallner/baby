Bugs, worst first

B1

A sleep left running is never capped, so it counts as sleep for every day until Wake is tapped

mediumconfirmededge
Impact

A forgotten Wake silently corrupts the sleep numbers a parent hands to the pediatrician (longest sleep stretch, sleep a day), and nothing on screen asks whether the baby is really still asleep. Parents forget Wake often, so the trigger is common even though the fix after the fact is a manual edit.

How it happens
  1. Tap Sleep on Log at night and forget to tap Wake.
  2. Keep using the app, or come back after 30 days away.
  3. Today's sleep total, History's day tiles and the Reports sleep figures count the open sleep up to now, so each following day shows a full 24 hours of sleep and the longest stretch grows without limit.
  4. Tap Wake: the entry is saved as one sleep as long as the whole gap, and stays in the log and the doctor PDF and CSV until the parent finds it in History and edits it.
Where
Shared/Services/NowSummary.swift:590Shared/Services/SummaryReport.swift:243Shared/Services/EventStore.swift:636
Suggested fix

Treat a running sleep older than a set limit (for example 12 hours) as needing attention: on foreground, show a one-line prompt on Log asking 'Still asleep?' with Wake at a chosen time, and cap the counted length in DayTally and SummaryReport at that limit.

Evidence
// NowSummary.swift:590 (DayTally.make)
case .sleep:
    // Sleep is credited to the day it happened in, split at midnight,
    // and never past now: an entry set to end later counts so far.
    let end = min(event.endedAt ?? (event.isRunning ? now : start), max(now, start))

// SummaryReport.swift:243
let finish = event.endedAt ?? (event.isRunning ? now : event.start)
guard finish > event.start else { return nil }
return (event.start, finish)

A running sleep has endedAt nil. Every tally and the report's sleep bouts substitute now for the missing end, with no ceiling on length. Nothing else ends or flags a timer: grep for stale or forgotten handling in Now, LogButtons, EventStore and LiveActivityService finds none (the Live Activity has staleDate nil), and stopRunning only sets endedAt to the Wake time. Feed timers have the same shape, but the Feed button logs an instant entry, so only sleep (and the editor's timed feed) is affected.

Checked by: Code reread of every reader of isRunning (NowSummary.swift:230,245,590,743; SummaryReport.swift:230,243; EventStore.swift:236,638,669).

Not proven: Read from code, not run: no gh-sim run was left to execute a test. Whether the owner wants a cap or prompt is a product call.

B5

Birth date moves a calendar day when the phone is more than 12 hours from where it was entered, and Settings then rewrites it

lowconfirmeddata
Impact

Day of life is one day off on a trip or for a partner far away in time, the checkup notes counted from the birth date (days 4, 14, 30) shift a day, the PDF DAY column is off by one, and merely opening Settings silently rewrites and syncs the birth date. The code comment and the 2026-10-21 note in interface.md say a time zone never moves the birth date. That only holds within 12 hours of the entering zone.

How it happens
  1. On a phone set to Los Angeles time, create a baby with birth date 1 January (Settings > Baby > Born, or onboarding).
  2. The birth date is stored as 12:00 noon Los Angeles, which is 05:00 on 2 January in Tokyo (and 01:00 on 2 January in Auckland for a London entry).
  3. Fly to Tokyo (or have a partner who joined the shared log live there). On the phone's local 2 January, open Now: it says Day 1, not Day 2. Settings > Baby > Birth date shows 2 January.
  4. Settings runs refreshChild on appear, which sets the date picker, which fires onChange(birthDate), which calls saveBirthDate. enteredBirthDate (noon on the displayed day in the new zone) differs from the stored value, so events.update writes a new birth date and CloudKit syncs it.
  5. Two parents 12 or more hours apart who each open Settings keep rewriting the same field, and each phone shows a different calendar date for it.
Where
Shared/Services/EventStore.swift:450Baby/Views/SettingsView.swift:94Baby/Views/SettingsView.swift:228Baby/Views/SettingsView.swift:247Shared/Utilities/DateHelpers.swift:15
Suggested fix

Make saveBirthDate compare calendar days (year, month, day) instead of instants, so opening Settings never rewrites the stored value. For the display, read the stored birth date's day in the zone it was written (for example by storing the day as three integers or a yyyy-MM-dd string next to the date) so travel cannot move it.

Evidence
/// A birth date is a calendar day. Kept at noon, so crossing a time zone
/// never moves it to the day before or after.
nonisolated static func noon(of date: Date?, calendar: Calendar = .current) -> Date? {
    date.map { calendar.date(bySettingHour: 12, minute: 0, second: 0, of: $0) ?? $0 }
}
// SettingsView.swift
.onChange(of: birthDate) { _, _ in saveBirthDate() }
private func saveBirthDate() {
    guard let child = events.child, enteredBirthDate != child.birthDate else { return }

Noon is only safe for offsets inside plus or minus 12 hours. Checked with Python zoneinfo: noon 1 Jan Los Angeles is 2 Jan 05:00 Tokyo; noon 1 Jan Tokyo is 31 Dec 19:00 Los Angeles; noon 1 Jan London is 2 Jan 01:00 Auckland. DateHelpers.dayOfLife and the Settings picker both read the stored instant with startOfDay in the current zone, so they land on the wrong day. SettingsView.refreshChild (line 219 to 220) assigns birthDate on appear, which triggers onChange, and saveBirthDate compares a fresh noon against the stored instant, which differs whenever the stored instant is not exactly noon in the current zone.

Checked by: Tests testProofP1BirthDateKeepsItsCalendarDayWhenThePhoneIsMoreThanTwelveHoursAway and testProofP1ReverseDirectionTokyoEnteredReadInLosAngeles failed as predicted (Tokyo reads Jan 2, Los Angeles reads Dec 31 for a Jan 1 birth date).

Not proven: The test was written but could not run (gh-sim could not authenticate, see gh_sim). Arithmetic confirmed with Python only. Whether SwiftUI fires onChange on the programmatic assignment in refreshChild is read from the code, not observed.

B6

A 2 AM day start drops yesterday's 2:00 to 3:00 entries from the totals on the US spring-forward morning

lowconfirmededge
Impact

Once a year, for people who chose a start hour of 2, for one hour, the daily count is short by whatever happened between 2:00 and 3:00 the day before. The count corrects itself at 3:00.

How it happens
  1. Settings > Daily totals > By day, pick a 2 AM start (the hour list offers 0 to 23).
  2. In a US zone, log a feed on Saturday 7 March 2026 at 2:30 AM.
  3. On Sunday 8 March, between 1:00 and 2:00 AM (before the clock jumps to 3:00), read Now, a widget or the Watch.
  4. Totals for 'Since 2 AM' leave out the 2:30 AM feed from the day before.
Where
Shared/Services/NowSummary.swift:660Shared/Services/NowSummary.swift:665Shared/Services/NowSummary.swift:666
Suggested fix

Compute the start as the latest day-start instant at or before now by stepping back one calendar day first and then setting the hour, or clamp the nonexistent hour to the day's first valid instant on both sides of the comparison.

Evidence
let today = calendar.date(bySettingHour: hour, minute: 0, second: 0, of: now) ?? calendar.startOfDay(for: now)
let start = today <= now ? today : (calendar.date(byAdding: .day, value: -1, to: today) ?? today)
let end = calendar.date(byAdding: .day, value: 1, to: start) ?? start.addingTimeInterval(24 * 3600)

On 8 March 2026 the local time 02:00 does not exist. Calendar.date(bySettingHour:) uses the nextTime policy, so 'today' becomes 03:00. At 01:30 that is later than now, so start is today minus one day, taken as 03:00 on 7 March, not 02:00. The 7 March window is [03:00, 03:00), which excludes 02:00 to 03:00 on 7 March. Reasoning on Foundation's documented default matching policy; not run.

Checked by: Tests testProofP2SinceTwoAMWindowAtOneThirtyOnSpringForwardKeepsYesterdaysTwoAM and testProofP2SpringForwardEntryAtTwoThirtyYesterdayIsCounted failed as predicted.

B8

'Day N' does not roll over at midnight on the Watch Today page, in widgets for up to an hour, or on Now with a non-midnight day start

lowplausiblestate
Impact

Cosmetic: the day-of-life number is one behind from midnight until the next entry, which for a night-feeding newborn is usually within a few hours. The counts do reset correctly (resetTodayIfNeeded); only dayOfLife is left out.

How it happens
  1. Baby born on day 3 of the log, phone and Watch paired. Last phone push at 11:30 PM.
  2. At 12:05 AM look at the Watch Today page: the title reads 'Today · Day 3' although it is day 4.
  3. It stays until the phone next republishes, which only happens when the summary content changes (a new entry).
  4. Same on Now: with Settings > Daily totals set to a 6 AM start (or Last 24 hours), the 30 second clock only reloads at 6 AM (and never for Last 24 hours), so the Day label stays old until a log, a foreground pass or an edit.
Where
Shared/Services/NowSummary.swift:222Shared/Services/NowSummary.swift:471BabyWatch/Views/WatchTodayView.swift:41BabyWidget/BabyWidget.swift:101Baby/Views/NowView.swift:70Baby/Views/NowView.swift:510
Suggested fix

Store the birth day (or the birth date) in the summary and derive dayOfLife in current(now:), the Watch heading and the widget view from now.

Evidence
summary.dayOfLife = child.dayOfLife(on: now, calendar: calendar)   // set once in make
func current(now: Date = .now, calendar: Calendar = .current) -> NowSummary {

NowSummary.current(now:) is what the Watch page, the complications and widget timeline entries use to age a summary, and it refreshes counts and the 24 hour list but not dayOfLife.
