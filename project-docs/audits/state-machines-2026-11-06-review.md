## What survived, ranked

1. **B2**, Last 24 hours totals on widgets, complications and the Watch never age out. Recurs every day for everyone on that setting with a widget or Watch, and the number it inflates is the one a doctor asks about. The audit ranked it second and called it cosmetic.
2. **B4**, Settings' reminder footer stays "Notifications are off" after the parent allowed them. Same population as B1, but it is what the parent sees, and it says their fix did not work.
3. **B1**, the foreground pass does not hand the reminder plan over after permission is allowed. One missed reminder, once per install, self-healing on the next tap. B1 and B4 share a cause and one fix (react to `scenePhase` in both places), so they can ship together.

## Audit product calls

1. Running timer returns after its button is turned back on: a fair call; `TrackedKinds` documents that entries come back.
2. Past visit date falls back to the birth-date schedule: fair. Minor addition: the picker's range starts at `Date.now` (`RemindersView.swift:220`) yet shows the stored past date.
3. Feed reminder counts from feed start and ignores sleep: documented (`Reminders.swift:143-144`, offer copy at `RemindersView.swift:122`), not a call to make.
4. Live Activity returns after a swipe: by design (`App.swift:114-118`).
5. Checkup note time after travel: a real, small defect rather than a product call (a time-interval trigger, `Reminders.swift:238`, fixed at scheduling). Rare.
6. The remove-in-completion race in `reschedule` (`Reminders.swift:219-228`): misfiled. It is an unproven code-path bug, not a product choice. Agreed it needs two plans inside one callback's latency, which no single tap produces; two processes (widget and app) rescheduling at once is the likeliest trigger and was not considered.

No serious state bug outside the audit's claims turned up in the code read for this review.

## Method changes

- **Cost the harm in the shipping UI before calling it a bug.** B3 is reachable, but the "permanent lost offer" disappears once you notice the offer was shown and answerable. Write the user-visible cost first; if it is "the user saw the thing at a slightly odd moment", it is not a bug.
- **Check the docs for a documented limit before filing.** B5's cause is stated in AGENTS.md and the interface rules. An invariant the auditor writes (I2, I6) is not a promise; cite the code or doc line that makes it one.
- **Rank by frequency times cost, and say which.** B1 happens once per install; B2 happens daily. The audit ranked the once-only bug first.
- **State the lifecycle assumption a repro depends on.** B1 is only a bug if the process survives the trip to iOS Settings. The audit's test proves `publish()` is skipped but not that the user's route keeps the process alive; that needed one line of reasoning in the claim.
- **Run the UI test the audit names.** B3 said "settle with a UI test" and gave the arguments; it took one gh-sim run. A code-path claim with a cheap headless check should run it before shipping the audit.
- **Keep product calls and unproven bugs apart.** Calls 5 and 6 are possible defects, not choices for Jack, and belong in a separate "unproven" list.
